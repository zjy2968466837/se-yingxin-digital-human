## 0 为什么需要本文

仓库当前是"9 个服务 1:1 同构的空壳"：每个业务服务只有 `XxxApplication` + `PingController` + `application.yml` + `Dockerfile`，横向基础能力**一项未落地**（无统一响应体、无全局异常、无鉴权、无 ORM 落地、无测试）。而 `AGENTS.md` 的约束 C-4 明确要求：

> 公共基础设施（统一返回体、全局异常、参数校验、JWT 鉴权）须先定统一方案再逐服务落地，不得各服务自建。

同时 `需求分析文档` 已在 IR / NFR 中写下一批**跨服务约定**（统一响应体、错误码分段、Bearer 鉴权、Header 透传），但它们目前只存在于文档——如果直接开工，谁先写谁事实上定标准，9 个服务必然漂移。本文就是把这批约定一次性定死。

## 1 横向能力框架

### 1.1 定义与判定标准

**横向能力（cross-cutting capability）**指与具体业务无关、但被多个服务共同需要、且必须保持一致形态的基础设施。与"纵向业务功能"（问答、报到、导航）正交。

判定标准，三条同时满足才算：

1. 被 **≥2 个服务**需要；
2. 一旦各写一套，问题会立即暴露（前端要适配多种响应结构、鉴权可被绕过、故障无法串联定位）；
3. 希望变更时**只改一处**。

### 1.2 能力清单（H-01 – H-14）

"归属"列中：`core` = `common-core` 模块，`web` = `common-web` 模块，`gw` = gateway，`svc` = 各业务服务，`fe` = 前端。

| 编号 | 能力 | 职责 | 归属 | 需求出处 |
|---|---|---|---|---|
| H-01 | 统一响应体 | 所有 HTTP 响应同一外壳；分页外壳 | core | IR-3.3 |
| H-02 | 错误码与全局异常 | 错误码分段、业务异常、异常 → 响应的统一转换 | core + web | IR-3.4 |
| H-03 | 参数校验 | 入参声明式校验与失败信息标准化 | web | NFR-5.5 |
| H-04 | 鉴权与会话 | 令牌签发/校验/续期/登出，网关统一拦截 | svc(auth) + gw | F1.8、F11.6、NFR-4.1 |
| H-05 | 用户上下文透传 | 网关解析后下发下游，下游只读 | core + gw + svc | IR-3.6 |
| H-06 | 链路追踪与日志 | traceId 贯穿、日志格式与级别、脱敏 | web + gw | NFR-4.6、F11.7 |
| H-07 | 数据访问基座 | 分页、审计字段填充、逻辑删除、事务边界 | web + svc | DR-1–DR-20 |
| H-08 | 缓存规范 | key 命名、序列化、TTL、失效策略 | web + svc | F3.12、NFR-2.4 |
| H-09 | 跨服务调用 | 调用方式、超时、降级、禁用场景 | web + svc | FR-2.8、D6 |
| H-10 | 接口文档 | 分组、注解、暴露范围 | web + gw | IR-3.7、NFR-5.4 |
| H-11 | 配置与启动契约 | 配置占位、profile、端口、健康检查 | svc | C-2、NFR-5.3 |
| H-12 | 测试基座 | 测试分层、命名、可被 CI 执行 | svc | NFR-5.6 |
| H-13 | 网关边界 | 路由、CORS、白名单、限流、响应体一致性 | gw | IR-3.1、F11.6 |
| H-14 | 前端请求与鉴权封装 | 请求实例、令牌存取、401 处理 | fe | NFR-3.x、NFR-4.1 |

### 1.3 公共模块划分（**决定**）

**决定：新增两个后端公共模块，纳入父 pom 的 `<modules>` 与 `dependencyManagement`。**

| 模块 | 内容 | 允许依赖 | 谁可以用 |
|---|---|---|---|
| `backend/common-core` | 响应体、错误码枚举、业务异常、常量、通用工具、用户上下文载体（纯 POJO） | 仅 JDK / Jackson / Lombok；**禁止 spring-web、spring-webmvc、servlet-api** | 全部 9 个服务 + gateway |
| `backend/common-web` | 全局异常处理、参数校验适配、用户上下文读取、traceId 过滤器、MyBatis-Plus 拦截器与审计填充、缓存配置骨架 | `common-core` + spring-web(mvc) + 持久层依赖 | 仅 8 个业务服务 |

依赖方向（**单向，不允许反向或横向依赖**）：

```
frontend ──► gateway ──► common-core
                 │
                 └──► 8 个业务服务 ──► common-web ──► common-core
```

**为什么必须拆两个**：gateway 基于 WebFlux（`spring-cloud-starter-gateway-server-webflux`），业务服务基于 Servlet MVC（`spring-boot-starter-web`）。若把 `@RestControllerAdvice`、`HttpServletRequest` 之类塞进单一公共模块并被网关依赖，**网关会因 servlet 栈缺失/冲突而启动失败**。同时 H-01 的响应体必须两端共用（网关鉴权失败也要返回同一结构），所以 `Result`/`ErrorCode` 必须落在无 web 依赖的 `core` 里。

### 1.4 边界：什么**不**进公共模块

- 业务实体、DTO、VO（各服务自己的领域模型）；
- 业务常量与枚举（如报到步骤定义）；
- 各服务的 `@SpringBootApplication`、Controller、Service、Mapper 接口与 XML；
- 服务专属配置类（如 qa-service 的 LLM 客户端配置）；
- 任何"只有一个服务用得上"的东西 —— 宁可先放服务内，出现第二个使用者再上移。

## 2 后端分层与包结构规范

### 2.1 分层职责（**决定**：四层 + 三类模型）

| 层 | 职责 | 禁止 |
|---|---|---|
| Controller | 参数接收与校验触发、调用 Service、返回 `Result` | 写业务逻辑、直接调 Mapper、出现 SQL |
| Service | 业务编排与事务边界、跨服务调用、缓存访问 | 直接拼 SQL、返回 `Result` 或 Entity 给 Controller |
| Mapper | 单表/多表数据访问（MyBatis-Plus + XML） | 写业务判断 |
| Entity | 与表结构一一对应的持久化对象 | 直接作为接口出入参 |

模型约定：`XxxDTO`（入参）、`XxxVO`（出参）、`XxxEntity`（持久化）。三者不合并，禁止 Entity 直接暴露给前端。

### 2.2 包结构与命名

```
com.sicnu.yingxin.<服务简称>
├── <服务>Application.java
├── controller/       XxxController
├── service/          XxxService（接口）+ impl/XxxServiceImpl
├── mapper/           XxxMapper（继承 BaseMapper）
├── entity/           XxxEntity
├── dto/              XxxRequest / XxxQuery / XxxDTO
├── vo/               XxxVO
├── config/           XxxConfig（服务专属）
├── client/           XxxClient（跨服务调用）
└── constant/         服务内常量
```

公共模块包根：`com.sicnu.yingxin.common.core.*`（`result`/`error`/`constant`/`util`/`context`）、`com.sicnu.yingxin.common.web.*`（`advice`/`filter`/`interceptor`/`config`）。

命名硬性约定：类名后缀必须表达类型（`Controller`/`Service`/`ServiceImpl`/`Mapper`/`Entity`/`DTO`/`VO`/`Config`/`Client`/`Filter`）；Java 注释用中文（沿用现有风格）。

### 2.3 事务与异常

- 事务注解只出现在 Service 的写方法上，禁止标在 Controller 或整个 Service 类上；
- 业务可预期失败抛业务异常（H-02），**禁止用返回 `null`/`false` 表达失败**；
- 跨服务调用**不放在事务内**（外部系统不可控，避免长事务），采用"先本地落库 → 再调用 → 失败补偿/标记"。

## 3 接口契约规范

### 3.1 路径与前缀（**决定**）

- 统一前缀 `/api/<服务简称>/**`，**网关转发不裁剪前缀**（IR-3.1，直连服务端口与走网关路径必须一致）；
- 资源名用**复数名词**：`GET /api/qa/questions`、`GET /api/qa/questions/{id}`；
- 动作型接口用子资源 + 动词：`POST /api/checkin/steps/{id}/checkin`（打卡）、`POST /api/aid/applications/{id}/review`（审核）；
- 查询参数用 query string，禁止在 GET 中传递敏感信息；
- 实时交互规划走 WebSocket（IR-3.2，F3.14），路径 `/api/qa/ws/**`。

### 3.2 统一响应体（**决定**）

所有接口（含网关自身产生的响应）返回 `{ code, message, data }`（IR-3.3）：

| 字段 | 类型 | 约定 |
|---|---|---|
| `code` | int | `0` 表示成功；非 0 见错误码分段 |
| `message` | string | 可直接展示给用户的中文提示；不含堆栈、SQL、类名 |
| `data` | object/array/null | 成功时的业务数据；失败时为 `null` |

分页统一外壳共用一个 `PageResult`：`{ list, total, page, size }`（`list` 为当前页数据数组）。转换适配在 Service 层完成。

**HTTP 状态码只表达传输语义**（**决定**）：

| HTTP | 语义 | 对应 code |
|---|---|---|
| 200 | 请求已被正确处理（业务失败也算） | `0` 或 `2xxx`/`4xxx` |
| 400 | 入参非法（校验不通过） | `3xxx` |
| 401 / 403 | 未认证 / 无权限 | `1xxx` |
| 404 | 路径不存在 | `9xxx` |
| 429 | 被限流 | `9xxx` |
| 5xx | 系统异常 | `9xxx` |

> 好处：前端只需判断 `code`，`request.js` 的拦截器逻辑保持单一分支。

### 3.3 错误码分段（**决定**：在 IR-3.4 基础上细化）

| 段位 | 含义 | 归属 |
|---|---|---|
| `0` | 成功 | — |
| `1001–1099` | 认证与会话：1001 未登录、1002 令牌无效或过期、1003 账号密码错误、1004 账号被禁用、1005 无权限访问 | 全局 |
| `2001–2099` | 通用业务错误：2001 资源不存在、2002 当前状态不允许该操作、2003 重复提交、2004 数据冲突 | 全局 |
| `2101–2199` | auth-service | FR-1 |
| `2201–2299` | qa-service | FR-3 |
| `2301–2399` | checkin-service | FR-2 |
| `2401–2499` | navigation-service | FR-4 |
| `2501–2599` | aid-service | FR-5 |
| `2601–2699` | life-service | FR-6 |
| `2701–2799` | content-service | FR-7 / FR-8 |
| `2801–2899` | admin-service | FR-9 |
| `3001–3099` | 参数与校验：3001 必填缺失、3002 格式非法、3003 取值越界、3004 长度超限 | 全局 |
| `4001–4099` | 外部依赖降级（前端展示降级提示，不阻断）：4001 财务、4002 地图、4003 LLM、4004 ASR/TTS、4005 微信接口、4006 学校身份源 | 对应服务 |
| `9001–9099` | 系统错误：9001 未捕获异常、9002 数据库异常、9003 缓存异常、9004 限流、9005 下游服务不可达 | 全局 + gw |

**段位即所有权**：一个服务只允许使用自己段位内的业务码，新增错误码必须先在本文附录登记，避免撞码。

### 3.4 幂等与写操作（**决定**）

- 打卡（F2.5）、申请提交（F5.5）、报修（F6.1）等**重复提交必须幂等**，返回首次结果而非报错；
- 幂等实现口径统一为**业务唯一键**（如 `用户 + 步骤`），不依赖前端防抖；
- 删除一律逻辑删除（见 §5.2），保证幂等与可追溯。

### 3.5 接口文档（IR-3.7）

- 每服务暴露 `/swagger-ui.html`，按服务名分组；
- 每个 Controller 必须有分组注解与接口说明，参数与响应字段需有中文描述，禁止"只有 ping 的空白文档"；
- 网关侧 Swagger 聚合作为可选优化，不阻塞开发。

## 4 鉴权与会话规范

### 4.1 令牌形态与生命周期（**决定**）

| 项 | 约定 |
|---|---|
| 形态 | JWT（HS256），负载含 `userId`、`role`、`exp`；**不放**姓名、学号、身份证等隐私字段 |
| 有效期 | 访问令牌 2 小时；临近过期由前端静默续期或后端下发新令牌（F1.8） |
| 会话存储 | Redis 保存 `jti → userId/role`，TTL 与令牌一致；**登出即删 key，令牌立即失效**（F1.8 验收准则） |
| 密钥 | 由环境变量注入（`JWT_SECRET`），不得写入仓库；长度 ≥ 32 字节 |
| 签发方 | 仅 auth-service 签发；其他服务**不签发、不解析** |

### 4.2 网关校验流程与白名单（**决定**，F11.6）

网关是唯一的鉴权入口，流程：**剥离入站用户头 → 取 `Authorization: Bearer` → 校验签名与有效期 → 校验 Redis 会话是否存在 → 注入用户上下文 → 转发**；任一环节失败直接返回 §3.2 约定的响应体，**请求不进入业务服务**。

白名单（只有这些路径免鉴权）：

| 路径 | 原因 |
|---|---|
| `/api/*/ping` | 连通性自检（F11.2） |
| `/api/auth/login/**`、`/api/auth/wechat/**` | 登录本身无需令牌（F1.1、F1.2） |
| `/api/public/**` | 面向家长/访客的公开内容（ACT-2，NFR-4.7） |

`/actuator/**`、`/swagger-ui.html` **不进白名单**：本地可临时放行，云端必须收敛（F11.7）。

### 4.3 用户上下文透传与防伪造（**决定**，IR-3.6）

- 网关注入的请求头（**固定名字，不得增删**）：`X-User-Id`、`X-User-Role`、`X-Trace-Id`；
- **网关必须先删除入站请求中同名头再注入**，否则外部可伪造身份——这是本方案的安全前提，实现评审时必查；
- 业务服务**只读 Header**，禁止自行解析 JWT、禁止自行校验令牌；
- 业务服务端口不对公网暴露（容器网络/安全组限制），仅网关可达。

### 4.4 前端令牌与 401（**决定**，H-14）

- 令牌以状态容器为唯一读写入口，`localStorage` 只做持久化，页面禁止直接操作存储；
- 请求拦截器统一附加 `Authorization`；
- 响应拦截器统一处理 `401`：清空令牌 → 跳转登录页并带上回跳地址；**不再逐个页面写判断**；
- 小程序端需同时处理 `401` 与 `403`，并避免在未登录时发起业务请求。

### 4.5 后台权限（NFR-4.4）

- 后台按角色（学工/后勤/保卫/学院）划分数据与功能权限，越权请求必须被拒绝并留痕；
- 权限判定在 admin-service，前端仅做菜单与按钮的显隐，**不作为安全边界**。

## 5 数据与持久化规范

### 5.1 库表命名（**决定**）

- 单一数据库 `yingxin`，**按服务分表**（同名服务前缀隔离，规避跨库分布式事务，NFR-2.3）；
- 表名 `<服务简称>_<实体复数>`：`auth_user`、`auth_identity`、`qa_question`、`checkin_progress`、`nav_poi`、`aid_application`、`life_repair_order`、`content_article`、`admin_role`；
- 表名与字段名**全小写 + 下划线**（本地 `lower_case_table_names=1`，与云端一致，写成驼峰在本地会静默通过、上线报错）；
- 字符集 `utf8mb4` / `utf8mb4_unicode_ci`；
- **禁止物理外键**（分表与迁移考虑），关联由应用层保证；
- 索引命名 `idx_<字段>`、唯一索引 `uk_<字段>`。

### 5.2 通用字段（**决定**）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键，统一使用分布式/雪花 ID，便于后续扩展 |
| `create_time` / `update_time` | DATETIME(3) | 由持久层自动填充，业务代码不得手写 |
| `create_by` / `update_by` | BIGINT | 操作人，取自用户上下文 |
| `deleted` | TINYINT(1) | 逻辑删除标记，默认 0 |

时间统一按 `Asia/Shanghai` 处理与展示（配置已就位）；金额用 `DECIMAL(10,2)`，禁止浮点；布尔字段用 `TINYINT(1)`。

### 5.3 表结构版本管理（**决定**）

- 引入 **Flyway**，采用**集中式迁移**：脚本统一放 `backend/db/migration/`，命名 `V<yyyyMMddHHmm>__<服务简称>_<说明>.sql`（时间戳版本号避免多人并行冲突）；
- 通过父 pom 的 `db` profile 执行迁移（`./mvnw -Pdb flyway:migrate`）；**业务服务不引 Flyway 依赖、不自动迁移**，避免 9 个服务争抢同一张 `flyway_schema_history`；
- `backend/init-sql/01-init.sql` 保持"只建库"，表结构一律走迁移脚本；
- 约定：**任何表结构变更都必须有对应的迁移脚本**，禁止手工改本地库后不写脚本。

### 5.4 缓存规范（**决定**，F3.12 / NFR-2.4）

- key 统一 `yx:<服务>:<业务>:<标识>`，全小写，禁止空格与中文；
- 值一律 JSON 序列化（禁用默认 JDK 序列化，否则 Redis 里是乱码）；
- **key 必须设 TTL**，禁止永久键（会话键 TTL 与令牌一致）；
- 数据变更后由**写入方主动失效**相关 key（改库即刻生效，F9.3 验收准则）；
- 缓存只做加速，**不得作为唯一数据源**；缓存不可用时须能回落数据库（NFR-2.2）。

### 5.5 敏感数据（**决定**，NFR-4.3）

- 身份证号、手机号、人脸相关数据、对话记录：入库加密存储，日志与接口响应中脱敏（保留必要前后缀）；
- 加密方式与密钥管理列入待决议（附录 B），但**"不落明文"是硬约束**；
- 家长/访客角色在任何接口上不得访问个人数据（NFR-4.7）。

## 6 日志与可观测性规范

| 项 | 约定 |
|---|---|
| traceId | 由网关生成并放入 `X-Trace-Id`，全链路透传；日志格式固定包含该字段，9 个服务的日志可串成一次请求 |
| 记录方式 | 统一用 `@Slf4j`，**禁止 `System.out` / `printStackTrace`** |
| 级别 | ERROR=需人工介入；WARN=可恢复异常或降级发生；INFO=关键业务节点（登录、提交、审核）；DEBUG=仅本地排查，生产不输出 |
| 内容 | 禁止打印令牌、密码、身份证、手机号全量；异常日志记录错误码与业务上下文，不打印堆栈给用户 |
| 健康检查 | 各服务保留 `/actuator/health`；生产对外仅暴露 `health`，`show-details=never` |
| 后续 | 集中日志与告警属 F11.7，待开发；本文先约束"日志可被采集"（统一输出到 stdout，容器友好） |

## 7 前端规范

### 7.1 通用（两端共同遵守）

- **网络访问只允许走 `api/` 层**：每个前端保留唯一请求实例（管理后台用 axios 封装，小程序用 `uni.request` 封装），页面/组件内禁止直接发请求；
- 目录约定：`api/`（按服务拆分）、`stores/`（状态）、`views/`（页面）、`components/`（通用组件）、`layouts/`（布局，管理后台需要抽公共布局）、`utils/`；
- 命名：页面 `XxxView.vue`、表单 `XxxForm.vue`、状态 `useXxxStore`；组件名多单词，避免与原生标签冲突；
- 令牌与 `401` 处理遵循 §4.4，禁止页面自行判断登录态；
- 新页面必须挂路由与菜单，不留"只有 URL 能进"的页面。

### 7.2 管理后台（admin-web）

- Element Plus 保持**全量注册**（现状），组件按需引入的优化不列入本期；
- 接口按服务拆分到 `api/<服务>.js`，与后端 `/api/<服务>` 前缀一一对应；
- 公共布局（侧边栏 + 顶栏 + 用户信息）抽为布局组件，禁止每个页面复制一套（现状 `DashboardView`、`QaView` 各写一份）。

### 7.3 小程序（miniprogram）

- 请求基地址**不得硬编码**（现状为 `http://localhost:8080/api`）：改为构建期环境变量或统一配置模块，区分开发与生产域名；
- 页面按功能域分包规划（问答、报到、导航、资助、生活、内容），避免主包体积超标（D7 难点）；
- 状态管理采用与 Vue3 配套的轻量方案，禁止在页面间用全局变量传数据；
- 真机调试所需的"不校验合法域名"只用于本地，不得写入交付说明之外的配置。

### 7.4 两端差异（**不得统一**）

两个前端的 Vite 版本不同（管理后台 8.x，小程序锁定 5.2.8），是上游 peerDependency 限制，详见 [开发环境版本](开发环境版本.md)。**禁止"顺手统一升级"**。

## 9 落地顺序与验收

**顺序（按依赖关系，不是按重要性）**：

| 阶段 | 内容 | 产出 |
|---|---|---|
| 0 | 评审并冻结本文 | 本文转"已生效" |
| 1 | 建立 `common-core` / `common-web` 骨架（H-01、H-02、H-03） | 两个模块 + 父 pom 纳管 |
| 2 | auth 签发 JWT + 网关鉴权过滤器（H-04、H-05、H-13） | 前端已有的 `Bearer` 链路被打通（F11.6） |
| 3 | Flyway 集中式迁移 + 首批表与种子数据（H-07、§5） | 第一批 DR 实体落库，虚构校园数据可配置 |
| 4 | 单服务纵向打样：qa-service 走通 Controller → Service → Mapper → Redis → 统一响应（H-06、H-08、H-12） | 一份可复制的样板 |
| 5 | 其余服务按样板铺开 | — |

**横向能力完成定义（DoD）**：

1. 任一接口（含异常路径）都返回 `{code,message,data}`；查不存在的资源得到业务码而非 500 堆栈；
2. 不带令牌访问受保护接口 → 网关直接 401，**业务服务日志中无该请求**；带令牌 → 下游能读到用户上下文；
3. 同一请求在网关与下游服务日志中的 traceId 一致；
4. 参数非法 → 400 且 `message` 指明具体字段；
5. 登出后旧令牌立即失效（F1.8 验收准则）；伪造 `X-User-*` 头进不来；
6. 至少一个服务有可被 CI 执行的单元测试。
