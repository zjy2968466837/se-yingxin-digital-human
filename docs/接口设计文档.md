# 迎新数字人系统 · 接口文档

> 项目：大学生迎新导引服务数字人系统（第 2 组）
> 版本：v1.0　2026-10-20
> 说明：字段名与仓库 `backend/db/migration/V1__init_schema.sql` 保持一致，照着表就能写代码。

---

## 1. 基本约定

### 1.1 地址

| 环境 | 地址 |
|---|---|
| 本地开发 | `http://localhost:8080/api/v1` |
| 线上 | `https://api.yingxin.example.com/api/v1` |

所有请求走网关 8080，网关负责鉴权、限流，再转发到各微服务。服务端口不对外。

### 1.2 请求格式

- 数据格式：JSON，UTF-8
- 请求体最大 1MB，文件走单独上传接口
- 必带头：

| Header | 说明 |
|---|---|
| `Authorization` | `Bearer <token>`，登录后拿到。白名单接口可以不传 |
| `X-Client-Version` | 客户端版本，如 `mp/1.2.0` |
| `X-Request-Id` | 建议传，链路排查用；不传服务端自己生成 |

### 1.3 数据类型

| 类型 | 怎么传 | 例子 |
|---|---|---|
| ID | **字符串**（雪花 ID 19 位，转数字会丢精度） | `"1836482910374629376"` |
| 时间 | UTC，ISO8601 带毫秒 | `"2026-10-20T07:19:48.000Z"` |
| 金额 | 字符串，单位分 | `"19900"` 表示 199.00 元 |
| 布尔 | `true` / `false` | `true` |
| 枚举 | 大写字符串，不做数字传输 | `"PAID"` |

前端存 ID 一律用字符串，别 `parseInt`。转成数字之后查出来的可能就变成别人的记录了。

### 1.4 统一返回

成功：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "request_id": "3f7a1c92-8e4b-4d1f-9a05-2c6d8e1b7f30"
}
```

失败：

```json
{
  "code": 10105,
  "message": "无权访问该资源",
  "data": null,
  "request_id": "3f7a1c92-8e4b-4d1f-9a05-2c6d8e1b7f30"
}
```

- `code = 0` 才算成功
- HTTP 状态码也会跟着改（400/401/403/404/409/429/500），别只看 HTTP 状态码
- `message` 是给用户看的中文提示，可以直接弹出来

### 1.5 分页、排序、过滤

分页：

```
GET /api/v1/admin/qa-questions?page=1&size=20
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `page` | 1 | 页码，从 1 开始 |
| `size` | 20 | 每页条数，最大 100 |

返回：

```json
{
  "code": 0,
  "data": {
    "items": [],
    "page": 1,
    "size": 20,
    "total": 137,
    "has_more": true
  }
}
```

前端做"加载更多"用 `has_more`，别用 `page * size < total` 算，翻页期间数据会变。

排序：

```
?sort=create_time         // 升序
?sort=-create_time        // 降序（负号）
?sort=-is_top,create_time // 多字段
```

排序字段只允许白名单里的，传别的返回 `10003`。每个列表接口下面会写清楚能排哪些。

过滤：字段名 + 值，范围查询用 `_from` / `_to`：

```
?status=PAID&create_time_from=2026-09-01T00:00:00.000Z&create_time_to=2026-09-30T23:59:59.999Z
```

## 2. 错误码

| code | HTTP | 含义 | 前端怎么办 |
|---|---|---|---|
| 0 | 200 | 成功 | 正常处理 data |
| 10001 | 400 | 参数格式不对 | 改参数，别重试 |
| 10002 | 400 | 参数超出范围 | 改参数 |
| 10003 | 400 | 不支持的字段或取值 | 查枚举表 |
| 10004 | 400 | 缺少必填参数 | 改参数 |
| 10005 | 413 | 请求体太大 | 减小内容 |
| 10101 | 401 | 没登录 / 没带 token | 跳登录页 |
| 10102 | 401 | token 过期 | 刷新，失败就跳登录 |
| 10103 | 401 | token 已失效（登出或被踢） | 跳登录页 |
| 10104 | 403 | 没这个功能的权限 | 提示，别重试 |
| 10105 | 403 | 这条数据不是你的 | 提示，别重试 |
| 10106 | 400 | 密码或验证码错误 | 让用户重输 |
| 20001 | 404 | 账号不存在 | 提示 |
| 20002 | 403 | 账号被冻结 | 联系管理员 |
| 20003 | 400 | 人脸核验没通过 | 重试或走人工 |
| 20011 | 409 | 正在处理，别重复提交 | 等一下看结果 |
| 20012 | 400 | 这步不在你的报到清单里 | 提示 |
| 20013 | 409 | 前面的步骤还没做完 | 引导去上一步 |
| 20041 | 409 | 已有一份没处理完的申请 | 跳已有申请 |
| 20042 | 409 | 当前状态不能做这个操作 | 刷新页面 |
| 20043 | 403 | 这个配置不允许改 | 提示 |
| 20051 | 409 | 相似的报修单已存在 | 跳已有单子 |
| 20061 | 404 | 内容不存在或还没发布 | 提示 |
| 50000 | 500 | 服务内部错误 | 可重试 2 次 |
| 50001 | 500 | 调用超时 | 可重试 |
| 50002 | 429 | 操作太频繁 | 按 Retry-After 等 |
| 50003 | 503 | 依赖服务不可用 | 走降级界面 |

判断规则很简单：`5xxxx` 可以重试，`1xxxx` / `2xxxx` 重试也没用。

## 4. 接口

### 4.1 认证（auth-service）

#### 4.1.1 学号登录

```
POST /api/v1/auth/login/student
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| student_no | string | 是 | 学号，10 位数字 |
| password | string | 是 | 密码 |
| device_type | string | 是 | `MP` / `H5` / `PC` |

```json
{
  "student_no": "2026010101",
  "password": "Yingxin@2026",
  "device_type": "MP"
}
```

返回：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIs...",
    "refresh_token": "rt_b7f3c1e24a5d4e8f",
    "expires_in": 7200,
    "token_type": "Bearer",
    "user": {
      "user_id": "1836482910374629376",
      "student_no": "2026010101",
      "real_name": "张*",
      "status": "NORMAL",
      "is_profile_complete": false
    }
  }
}
```

`real_name` 是脱敏的。`is_profile_complete=false` 时引导用户去补档案。

同 IP 一分钟超过 10 次返回 `50002`。

#### 4.1.2 微信登录

```
POST /api/v1/auth/login/wechat
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| code | string | 是 | `wx.login()` 拿到的 code，5 分钟有效 |
| device_type | string | 是 | `MP` |

返回同 4.1.1，多一个 `is_new_user`，为 true 时前端引导去身份核验。

#### 4.1.3 发验证码

```
POST /api/v1/auth/sms-code
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| phone | string | 是 | 11 位手机号 |
| scene | string | 是 | `LOGIN` / `RESET_PWD` / `BIND_PHONE` |

```json
{ "code": 0, "data": { "expires_in": 300 } }
```

同一手机号 60 秒一次，一天 10 次。

#### 4.1.4 刷新 token

```
POST /api/v1/auth/refresh
```

| 参数 | 类型 | 必填 |
|---|---|---|
| refresh_token | string | 是 |

返回新的 `access_token` + `refresh_token`。旧的 refresh_token 用完就失效，重复用会判定泄露，该用户所有 token 一起作废。

#### 4.1.5 登出

```
POST /api/v1/auth/logout
```

不带参数。服务端把当前 token 的 `jti` 拉黑，登出后旧 token 立刻不能用。返回 204。

#### 4.1.6 当前用户信息

```
GET /api/v1/auth/me
```

```json
{
  "code": 0,
  "data": {
    "user_id": "1836482910374629376",
    "student_no": "2026010101",
    "real_name": "张*",
    "phone": "138****8888",
    "profile": {
      "edu_level": "UNDERGRAD",
      "college": "计算机学院",
      "major": "软件工程",
      "class_name": "软件 2601",
      "dorm_building": "紫荆 3 号楼",
      "dorm_room": "302",
      "batch_id": "1836482910374610000",
      "admission_type": "REGULAR"
    },
    "missing_fields": ["phone"],
    "visible_modules": ["CHECKIN", "NAV", "QA", "AID", "LIFE", "CONTENT"]
  }
}
```

档案字段缺就是 `null`，不报错。`missing_fields` 是缺哪些，`visible_modules` 是前端该显示哪些模块——缺宿舍号就别显示宿舍相关入口。

#### 4.1.7 补全档案

```
PATCH /api/v1/profile
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| edu_level | string | 否 | `UNDERGRAD` / `GRADUATE` / `OTHER` |
| college | string | 否 | 学院 |
| major | string | 否 | 专业 |
| class_name | string | 否 | 班级 |
| dorm_building | string | 否 | 宿舍楼 |
| dorm_room | string | 否 | 房间号 |
| admission_type | string | 否 | `REGULAR` / `SPECIAL` / `OTHER` |
| phone | string | 否 | 要配合 4.1.3 的验证码 |

只改传上来的字段，没传的不动。

#### 4.1.8 人脸核验

```
POST /api/v1/auth/face/verify
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| image_base64 | string | 是 | 图片 base64，不超过 512KB |
| liveness_score | number | 否 | 前端活体分，0~1 |

```json
{ "code": 0, "data": { "is_passed": true, "similarity": 0.92, "mode": "MOCK" } }
```

课程阶段没有真人脸 SDK，`mode` 返回 `MOCK`。接口按真实形态定好，以后接 SDK 只换实现。

#### 4.2.3 打卡

```
POST /api/v1/checkin/steps/{step_code}/checkin
```

路径参数 `step_code`：步骤编码，如 `PAY`。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| checkin_channel | string | 是 | `SELF_CONFIRM` 自己确认 / `SCAN` 现场扫码 |

```json
{ "checkin_channel": "SELF_CONFIRM" }
```

第一次打卡：

```json
{ "code": 0, "message": "打卡成功", "data": { "step_code": "PAY", "status": "COMPLETED", "checkin_time": "2026-10-20T07:19:48.000Z", "is_duplicated": false } }
```

重复打卡（不报错）：

```json
{ "code": 0, "message": "该步骤已完成", "data": { "step_code": "PAY", "status": "COMPLETED", "checkin_time": "2026-09-15T03:10:00.000Z", "is_duplicated": true } }
```

重复打卡返回成功是有意的：用户要的结果已经达成了，报错只会让他以为没打上，然后继续点。

防重复用三层：前端按钮置灰、`Idempotency-Key`、数据库唯一索引 `uk_user_step(user_id, step_code, deleted)`。前两层并发下都会漏，真正管用的是唯一索引。

### 4.3 智能问答（qa-service）

#### 4.3.1 创建会话

```
POST /api/v1/qa/sessions
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| channel | string | 是 | `MP` 小程序 / `PC` 大屏 / `H5` |

```json
{ "code": 0, "data": { "session_id": "1836482910374629600", "start_time": "2026-10-20T07:19:48.000Z", "expires_in": 1800 } }
```

游客也能问，`user_id` 为空。上下文 30 分钟过期。

#### 4.3.2 提问

```
POST /api/v1/qa/ask
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| session_id | string | 是 | 会话 ID |
| question | string | 是 | 1~200 字 |
| content_type | string | 否 | `TEXT`（默认）/ `RICH` |

```json
{ "session_id": "1836482910374629600", "question": "学费最晚什么时候交啊" }
```

返回：

```json
{
  "code": 0,
  "data": {
    "message_id": "1836482910374629700",
    "hit_type": "QA_LIB",
    "answer_type": "RICH",
    "question_id": "1836482910374629800",
    "category": "PAYMENT",
    "confidence": 0.93,
    "cost_ms": 42,
    "answer_text": "学费请在报到当天 17:00 前缴清，线上通过财务处公众号缴纳。",
    "answer_media": [
      { "type": "flow", "content": "① 进入公众号 → ② 校园缴费 → ③ 输入学号 → ④ 确认金额 → ⑤ 支付" },
      { "type": "image", "url": "https://cdn.example.com/qa/pay-guide.jpg" }
    ],
    "suggestions": ["怎么查缴费是否成功", "可以分期吗", "绿色通道怎么申请"],
    "digital_human": { "speech_text": "学费请在报到当天 17:00 前缴清……", "emotion": "HAPPY" }
  }
}
```

`hit_type` 说明答案从哪来：

| 值 | 含义 | 前端怎么处理 |
|---|---|---|
| `CACHE` | 命中 Redis 热点缓存 | 正常展示，`is_cached=true` |
| `QA_LIB` | 问答库命中 | 正常展示 |
| `LLM` | 问答库没有，大模型兜底 | 展示，并标注"AI 生成，仅供参考" |
| `MISS` | 没答上 | 显示"没听懂" + 转人工按钮 |

`answer_type` 是 `TEXT` 时只看 `answer_text`，`RICH` 时再按顺序渲染 `answer_media` 里的块（`image` / `flow` / `video` / `poi`）。

性能要求：问答库命中 P99 小于 1 秒，缓存命中约 10 毫秒，大模型 3 秒超时就返回 `MISS`，不要无限等。

```

```

| 参数 | 类型 | 必填 | 说明 |

| reason | string | 否 | 申请理由，不超过 512 字，加密存储 |

{

  "data": {
    "apply_id": "1836482910374631200",
    "status": "WAIT_REVIEW",
    "submit_time": "2026-10-20T07:19:48.000Z"
  }
}
```

同一批次、同一政策只能申请一次，靠唯一索引 `uk_user_policy_batch` 兜住。重复提交返回 `20041` 和已有单号。

#### 4.5.5 我的申请

```
GET /api/v1/aid/applies?status=WAIT_REVIEW&page=1&size=20
```

`sort` 白名单：`create_time`、`submit_time`。这个接口要加 `Cache-Control: no-store`，用户数据不能进共享缓存。

#### 4.5.6 申请详情

```
GET /api/v1/aid/applies/{apply_id}
```

查出来之后必须校验 `user_id` 是不是当前用户，不是就返回 `10105`。

不校验就是标准的水平越权：把 URL 里 ID 改一下就能看见别人的家庭情况。这比订单数据敏感得多。

#### 4.5.7 后台：申请列表

```
GET /api/v1/admin/aid/applies
```

参数：`status`、`policy_id`、`apply_type`、`college`、`keyword`（学号/姓名）、`submit_time_from` / `submit_time_to`、分页排序。

`college` 受数据权限限制，学院管理员只能看自己学院，服务端强制加条件，不靠前端传。

#### 4.5.8 后台：审核

```
POST /api/v1/admin/aid/applies/{apply_id}/review
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| action | string | 是 | `APPROVE` / `REJECT` |
| reject_reason | string | 否 | 驳回时必填，不超过 255 字 |

状态流转：

```
WAIT_REVIEW --通过--> APPROVED
WAIT_REVIEW --驳回--> REJECTED --重新提交--> WAIT_REVIEW
WAIT_REVIEW --用户撤回--> WITHDRAWN
```

不在上面的流转一律返回 `20042`，别只靠前端把按钮禁掉。每次审核写一条操作日志。

## 6. 写接口时注意这几件事

1. **用户 ID 从 token 取，不接受前端传。** 参数里出现 `user_id` 的接口，一律改成从登录态读。
2. **查详情要校验归属。** 列表可以用 `WHERE user_id = ?` 一次性兜住，详情必须显式比一次。
3. **列表必须分页，排序字段必须白名单。** 直接拼 `ORDER BY` 是注入入口。
4. **写接口要有幂等。** 打卡、申请、报修都用唯一索引兜底，别只靠代码判重。
5. **错误信息不要带堆栈和 SQL。** 统一异常处理，返回中文提示 + `request_id`。
6. **token 不放 URL。** 会进 nginx 日志、浏览器历史、Referer，等于公开。

  → 后台登录 → 看板 → 日志 → 配置
```

每个模块做完，用 Apifox 存一条测试用例，跑通再说下一个。前端后端各写各的、最后一天合，基本上就是通宵。

## 8. 上线前自查

| 序号 | 检查项 |
|---|---|
| 1 | URL 是小写复数名词，动作用 HTTP 方法表达 |
| 2 | 状态码用对（200/201/204/400/401/403/404/409/429/500） |
| 3 | 返回统一是 `code/message/data` |
| 4 | 错误码能看出是参数错还是系统错 |
| 5 | 列表有分页、排序、过滤 |
| 6 | 写接口做了幂等 |
| 7 | ID 传字符串、时间是 UTC、金额用分 |
| 8 | 管理接口都在 `/admin/**`，且做了权限校验 |
| 9 | 查数据校验了归属 |
| 10 | 列表接口跑过 P99，慢查询有日志 |

前 5 条不过，前端联调会很难受。后 5 条不过，上线会出事。
