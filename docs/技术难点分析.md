# 技术难点分析与拆分 —— 大学生迎新导引服务数字人系统

> 版本：v1.0 ｜ 配套文档：[需求规格说明书](需求规格说明书.md)、[功能清单与分解](功能清单.md)、[项目计划](项目计划.md)
> 用途：识别项目关键难点，拆解为可独立验证的子问题，明确降级方案，为 M4 前技术验证（Spike）与任务分配提供依据。

## 0. 说明

### 0.1 拆分原则

1. **每个难点必须可独立验证** —— 拆到"能单独跑一个 demo 证明可行"的粒度；
2. **每个难点必须有降级形态** —— 攻不下来时系统仍可演示（呼应 [项目计划](项目计划.md) 的风险应对策略）；
3. **优先暴露最危险的部分** —— 采用 Spike 方式先验证高风险项，而非按功能顺序开发。

### 0.2 难度 / 影响分级

| 标记 | 难度（实现复杂度） | 影响（不解决时的后果） |
|------|-------------------|----------------------|
| ★★★★★ | 需外部资源或研究级能力 | 核心链路不可演示 |
| ★★★★ | 需选型 + 自研算法 | 主要功能缺失 |
| ★★★ | 工程量大但路径明确 | 体验下降，可降级 |
| ★★ | 主要是人力/内容投入 | 内容空洞但不阻塞 |

### 0.3 与功能清单的关系

本文的难点 ID（`D<n>`）与 [功能清单](功能清单.md) 的功能 ID（`F<模块>.<序号>`）交叉引用。一个难点通常横跨多个功能项，一个功能项也可能受多个难点约束。

## 2. 难点详细拆分

### D1 数字人形象与实时交互

**为什么难**：[项目计划](项目计划.md) 风险登记中唯一"概率高 + 影响高"的项。难点不在单点技术，而在**形象方案决定了整条渲染/音频/交互链路**，方案未定则后续无法开工。

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 验证方式 | 降级形态 |
|----|--------|-----------|---------|---------|
| D1-a | 形象方案选型 | 3D 需建模 + Three.js 渲染管线；Live2D 模型资源获取受限；厂商 SDK 有资质/费用门槛 | 各方案各跑一个最小 demo 并排对比 | 2D 静态图 + 预渲染说话视频（无交互口型） |
| D1-b | 渲染位置 | 前端渲染吃移动端性能；云端推流需 GPU 实例（成本 + 运维） | 前端渲染帧率与内存实测 | 只在前端渲染，不引入云推流 |
| D1-c | 口型与动作同步 | 需 TTS 音频的音素/时间戳与口型帧对齐，自研成本高 | 播一段 TTS 观察口型是否跟得上 | 使用厂商 SDK 内置口型；再降级为"说话时随机张嘴动画" |
| D1-d | 小程序端承载 | 微信小程序包体积限制、WebGL 能力、iOS 内存与后台回收 | 真机（iOS + Android）跑形象 demo | 形象资源走 CDN，首屏静态图渐进增强 |
| D1-e | 状态机与业务耦合 | 数字人需表达"思考中/播报中/等待输入"等状态，与问答异步结果耦合 | 单轮对话状态流转走查 | 简化为三态：待机 / 播报 / 加载 |

#### 关键依赖

`D1-a 未定 → D1-b/c/d 无法开工`。因此 D1-a 是**整个项目的头号 Spike**。

---

### D2 智能问答的"准"与"快"

**为什么难**：需求同时要求"口语化理解"（准）与"响应 < 2s"（快）、"后台改库即时生效"（一致）与"缓存热点"（快）。这四者天然互相拉扯。

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 应对策略 |
|----|--------|-----------|---------|
| D2-a | 意图理解 | 中文口语化表达无关键词可匹配（"在哪领被子""饭卡怎么充"） | 同义词/别名映射表起步；用问答库的分类标签做粗意图路由 |
| D2-b | 混合路由与阈值 | 问答库命中与 LLM 兜底的边界（置信度阈值如何定） | 阈值配置化；未命中问题全部落库，用真实数据回调阈值 |
| D2-c | 多轮对话 | 追问、澄清、槽位补全需要会话状态机 | 一期只做"单轮 + 关键词拼接"，多轮后置（F3.5 定 P1） |
| D2-d | 响应时延 | LLM 天然 1–3s，与 NFR-1（<2s）冲突 | **问答库优先命中**（Redis 缓存命中 ~10ms）；LLM 设超时，超时返回"稍后回复 + 兜底话术" |
| D2-e | 缓存一致性 | NFR-4 要求后台改库即时生效，Redis 缓存会造成脏读 | 改库主动失效对应 key；key 带内容版本号 |
| D2-f | 内容冷启动 | 问答库条目是人力产出，无内容即无命中率 | 从迎新官网/学生手册批量录入；提供批量导入接口（F9.3） |
| D2-g | 答案富媒体 | 答案可能是图片/流程图/短视频/地图点位，数据结构不统一 | 答案定义统一为"结构化 block 列表"，前端按 type 渲染 |

> D2-f 是**非技术难点但直接决定演示效果**，需要尽早安排内容整理的人力。

### D3 语音链路（ASR / TTS / 口型）

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 应对策略 |
|----|--------|-----------|---------|
| D3-a | 录音与格式 | 小程序录音格式（mp3/aac/pcm）、采样率与 ASR 要求不一致 | 统一转 16kHz PCM 再送识别 |
| D3-b | 流式 vs 整段 | 流式识别体验好但接入复杂、延迟调优难 | 一期做"整段识别"（按下-松开-识别），验收达标即可 |
| D3-c | 口音与环境噪音 | 迎新现场嘈杂，识别率骤降 | 语音定位为**辅助入口**，文字输入为主链路 |
| D3-d | 供应商与资质 | 微信同声传译插件能力有限；云厂商 API 涉及费用与网络可达性 | 先定义 ASR/TTS 抽象接口 + mock 实现，再插厂商 SDK |
| D3-e | 与数字人时序耦合 | TTS 音频长度决定播报时长，需驱动口型与字幕同步 | 一期文字气泡与语音并行，不做逐字同步 |

### D4 校园导航（室内 / AR）

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 应对策略 |
|----|--------|-----------|---------|
| D4-a | 地图与 POI 数据 | 学校真实底图/点位拿不到，POI 录入工作量大 | 建**虚构校园数据包**，全量走配置表，后期替换真实数据零改动 |
| D4-b | 路径规划算法 | 需图数据建模 + 最短路（A*/Dijkstra），还要处理步行/通勤车多种方式 | 自研轻量图算法（节点+边+权重），不引入专业路径引擎 |
| D4-c | 室内导航 | 室内无 GPS，精确引导需蓝牙信标/WiFi 指纹 → 硬件成本 | **降级为"楼栋楼层图 + 静态指引"**，不做实时室内定位 |
| D4-d | 地图 SDK 选型 | 腾讯位置服务 vs 高德；小程序地图组件能力受限（自定义图层、覆盖率） | 小程序生态优先腾讯；路线用 `polyline` 绘制 |
| D4-e | AR 实景导航 | 需 SLAM/VIO 视觉定位，属研究级难度 | **明确列为纯加分项，可不实现**（F4.9 为 P2） |
| D4-f | 数字人带路文案 | 需把路径转为自然语言（"左转 50 米到达 XX"）并与语音播报联动 | 路径节点 → 文案模板，距离取整后套模板 |

### D5 身份核验与合规

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 应对策略 |
|----|--------|-----------|---------|
| D5-a | 学校统一认证对接 | 需学校信息中心配合提供 CAS/OAuth 接口，课程项目拿不到 | 抽象认证适配层；本地用模拟账号数据，文档写明生产对接方式 |
| D5-b | 人脸核身资质 | 微信人脸核身接口需**企业主体资质** | 降级为模拟核验（UI 保留、逻辑直接通过） |
| D5-c | 微信登录与绑定 | openid/unionid 与学号的绑定关系、会话过期与刷新 | JWT + Redis；`openid ↔ 学号` 绑定表落库 |
| D5-d | 敏感信息合规 | 身份证、人脸、对话记录属个人信息，需加密存储 + 传输加密 | 落库字段加密、传输 HTTPS；对话记录不落敏感原文；文档说明合规边界 |
| D5-e | 身份信息解析 | 需从身份源解析出本科/研究生、学院专业、宿舍楼栋、报到批次 | 解析规则配置化，缺失字段降级为空并在 UI 隐藏对应模块 |

### D6 微服务联调与跨服务一致性

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 应对策略 |
|----|--------|-----------|---------|
| D6-a | 跨服务业务闭环 | 报到进度(checkin) ⟷ 缴费状态 ⟷ 绿色通道(aid) 存在跨服务状态流转 | 服务拆分但**同库分表**，用本地事务规避分布式事务 |
| D6-b | 服务发现 | 当前无注册中心，地址硬编码 | 不建议引入 Nacos（课程项目过度设计）；本地直连，云上用容器名/环境变量 |
| D6-c | 网关鉴权与 WebSocket | 网关统一校验 JWT；WebSocket 经网关转发需处理握手鉴权 | 先打通 HTTP 全链路，WS 单独立项（F3.14 为 P1） |
| D6-d | 本地资源占用 | 9 个 JVM 同时启动内存吃紧 | 按需启动 + 限制堆内存；文档给出"最小启动集" |
| D6-e | 用户上下文透传 | 服务间需感知当前用户，避免重复解析 | 网关解析 JWT 后写请求头下发，下游服务只读 Header |
| D6-f | 统一基础设施缺失 | 无统一返回体/异常处理/参数校验，易出现各服务各写一套 | **先定统一方案再逐服务落地**（见仓库 AGENTS.md 明确要求） |

### D7 多端适配与微信平台约束

#### 子问题拆解

| ID | 子问题 | 具体难在哪 | 应对策略 |
|----|--------|-----------|---------|
| D7-a | 域名强制要求 | 小程序仅允许 HTTPS + **已备案域名**，本地 IP/localhost 不可用 | 开发期勾选"不校验合法域名"；演示用 Azure HTTPS 域名 |
| D7-b | uniapp 多端差异 | 一套代码编译小程序/H5，条件编译与 API 差异易踩坑 | 一期只保证小程序端；H5 后置 |
| D7-c | 依赖版本冲突 | uni-app 的 Vite 被死锁在 5.2.8，与 admin-web 的 Vite 8 不同，不可"统一升级" | 维持现状，两个前端项目独立管理 |
| D7-d | 大屏端交互 | PC 大屏（语音 + 触控 + 常驻）与小程序交互范式差异大 | 复用后端 API，UI 单独实现（F10.7 为 P2） |
| D7-e | 真机与工具差异 | 开发者工具正常但真机出现网络/权限问题 | 每个版本做一次真机冒烟 |

### D8 内容与数据冷启动

**为什么列进来**：这不是技术难点，但是**唯一无法用技术手段绕过的阻塞项** —— 没有数据，所有页面都是空的。

| ID | 子问题 | 应对策略 | 责任方向 |
|----|--------|---------|---------|
| D8-a | 报到流程与步骤数据 | 虚构一套标准流程（7 步），步骤模板配置化 | 数据/运维 |
| D8-b | 问答库条目 | 按知识域分组批量录入，先覆盖高频 TOP 50 | 后端 B + 数据 |
| D8-c | 校园地图 POI | 虚构校园 + 20~30 个关键点位 | 数据/运维 |
| D8-d | 安全/社团/生活内容 | 分类整理，注明内容来源 | 内容方向 |
| D8-e | 数据可替换性 | 全部走配置表/种子 SQL，替换真实数据不改代码 | 全员约定 |

## 4. Spike 验证计划（M4 前置）

> 原则：**先验证最危险的，而不是先开发最紧急的**。每个 Spike 只求"跑通证明可行"，不追求完成度。

| 顺序 | Spike 目标 | 验证的子问题 | 通过准则 | 不通过时的走向 |
|------|-----------|-------------|---------|---------------|
| 1 | 数字人在小程序中跑起来 | D1-a/b/d | 真机可加载形象并播放一段话 | 降级 2D 静态图 + 预渲染视频 |
| 2 | 问答库命中 + LLM 兜底各一次 | D2-a/b/d | 命中走缓存、未命中走 LLM，均能返回答案 | 关闭 LLM，纯问答库 + 兜底话术 |
| 3 | 地图上画出两点间路径 | D4-b/d | 小程序地图组件渲染出 polyline | 改为静态楼层图 + 文字指引 |
| 4 | 登录 → 报到进度 → 问答 全链路打通 | D5-a、D6-a/c/e | 一个模拟账号可走通三个服务 | 合并服务或改为网关内直连 |

**Spike 产出要求**：每个 Spike 结束后更新本文档对应子问题的结论（可行 / 需降级 / 弃用），并把结论回写到 [功能清单](功能清单.md) 的状态列。

## 5. 降级矩阵（最终兜底形态）

若若干难点无法攻克，系统仍可演示的**最低可接受形态**：

| 模块 | 完整形态 | 兜底形态 |
|------|---------|---------|
| 数字人 | 3D 实时交互 + 口型同步 | 2D 形象 + 文字气泡 + 预录语音播放 |
| 问答 | LLM + 多轮 + 语音 | 问答库关键词命中 + 文字形式 + 未命中引导联系辅导员 |
| 导航 | AR 实景 + 室内定位 | 静态地图 + 点位列表 + 文字路线描述 |
| 身份核验 | 人脸核身 + 统一认证 | 模拟账号登录 + 身份信息预置 |
| 资助/生活/安全 | 在线申请 + 审核闭环 | 政策展示 + 办理入口跳转（线下办理） |
| 管理后台 | 全量配置 + 分权 + 统计 | 问答库管理 + 公告发布 |

> 兜底形态覆盖需求规格说明书第 2 章的全部 10 项核心功能，可保证 **M7 测试交付** 有完整可演示系统。

## 6. 对风险登记的补充建议

在 [项目计划](项目计划.md) 的风险表基础上，建议新增/细化为：

| 风险 | 概率 | 影响 | 应对（本文对应） |
|------|------|------|-----------------|
| 数字人方案选型拖延导致后续链路无法开工 | 高 | 高 | D1-a 列为头号 Spike，设硬性决策点 |
| 问答库无内容导致命中率为零 | 高 | 高 | D2-f/D8-b，提前安排内容录入人力 |
| 室内定位硬件成本超出课程项目预算 | 高 | 中 | D4-c 直接降级为静态指引 |
| 团队成员各自实现基础设施导致返工 | 中 | 中 | X4，先定统一方案再落地 |
