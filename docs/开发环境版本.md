# 开发环境版本

本文是**环境一致性的人工清单**。项目要保证：所有成员不管用 WSL 还是 Windows，构建产物与行为一致。

> 原则：**版本只在一处定义，不要手改同步**。下面的"事实来源"文件才是真正的约束，
> 本文只是给人看的汇总。改版本时：先改事实来源文件，再回来更新本表。

## 一、事实来源（机器可读，别手改）

| 约束对象 | 事实来源文件 |
|----------|--------------|
| JDK / Node | `.tool-versions`、`.nvmrc`、`.node-version` |
| Maven | `backend/.mvn/wrapper/maven-wrapper.properties`（mvnw 自动下载对应版本） |
| 后端依赖（Spring Boot/Cloud 等） | `backend/pom.xml` 的 `<properties>` 与 `<parent>` |
| 前端工具链（Node 最低版本、pnpm 版本） | 各 `frontend/*/package.json` 的 `engines` / `packageManager` |
| 前端依赖精确版本 | 各 `frontend/*/pnpm-lock.yaml`（**不要手改**，用 `pnpm install` 更新） |
| MySQL / Redis 版本 | `backend/docker-compose.yml` 的 `image:` |
| 换行符 / 编码 / 缩进 | `.gitattributes`、`.editorconfig` |

## 三、改版本时的操作流程

1. 改对应的**事实来源文件**（见第一节表格）
2. 前端依赖改动后执行 `pnpm install` 让锁文件同步（**不要手改 pnpm-lock.yaml**）
3. 本地跑一遍验证：
   ```bash
   cd backend && ./mvnw clean install -DskipTests
   cd frontend/admin-web && pnpm install --frozen-lockfile && pnpm build
   cd frontend/miniprogram && pnpm install --frozen-lockfile && pnpm build:mp-weixin
   ```
4. 回到本文更新第二节的表格
5. 推送到 `dev` / `main`，由 CI 复核

## 四、CI 会检查什么

`.github/workflows/build.yml` 在推送 `main`/`dev` 与 PR 时自动运行，在干净环境里验证：

- 后端：JDK 17 + `./mvnw` 构建全部 9 个模块
- 两个前端：`pnpm install --frozen-lockfile`（锁文件不匹配即失败）+ 构建

**它抓不到的情况**：成员本机工具链版本不对（CI 是干净环境，不代表成员机器）。
这部分靠上面的声明文件 + 本文档约束，属于人工责任。
