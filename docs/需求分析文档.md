### 1.2 项目背景

高校新生报到是典型的**短周期、高并发、强流程**场景：数千名新生在 2–3 天内集中到校，需依次完成预报到、缴费、绿色通道、领物资、入住、人脸采集、校园卡激活等环节；而报到政策、办理地点、材料清单等信息分散在官网、公众号、纸质须知、辅导员通知等渠道，新生往往"不知道下一步做什么、去哪做、要带什么"。

传统做法依赖现场志愿者一对一答疑，存在三个结构性问题：

1. **人力瓶颈** —— 咨询集中在少数高峰时段，志愿者数量与咨询量不匹配；
2. **信息不一致** —— 同一问题在不同渠道的答复口径存在差异；
3. **覆盖时长不足** —— 报到前后（尤其夜间与线上预报到阶段）缺乏即时答疑手段。

本项目以**数字人**为统一交互入口，整合迎新政策、报到流程、校园导航、资助与绿色通道、生活服务、安全教育、社团与入学适应等内容，提供 7×24 小时语音 / 文字交互与主动引导，作为线下志愿者的补充而非替代。

## 2 总体描述

### 2.1 系统目标

| 编号 | 目标 | 说明 | 衡量方式 |
|---|---|---|---|
| G1 | 提供 7×24 小时迎新咨询入口 | 新生在任意时段可获得即时答复，无需等待人工 | 可用性监测 + 用户测试 |
| G2 | 打通报到全流程导引 | 新生按步骤完成 7 个报到环节并有明确进度反馈 | 报到完成率统计 |
| G3 | 统一信息口径 | 所有答复源自后台可维护的问答库与内容库 | 后台改库后前端即时生效 |
| G4 | 降低现场答疑压力 | 高频问题由系统承接，人工只处理复杂与异常场景 | 未解答转人工比例 |
| G5 | 形成可复用的服务框架 | 跨服务架构清晰，内容可配置，真实数据可替换 | 数据替换不改代码 |

### 2.2 用户角色与特征

| 编号 | 角色 | 特征与诉求 | 主要使用端 | 权限范围 |
|---|---|---|---|---|
| ACT-1 | 新生 | 系统第一用户；到校前后集中使用；不熟悉校园，问题口语化、碎片化；部分学生经济困难需资助 | 学生端网页（移动浏览器优先） | 本人身份信息、本人报到进度、公开内容 |
| ACT-2 | 家长 / 访客 | 只读咨询；关心报到安排与安全；不涉及个人隐私数据 | 学生端网页（公开内容区） | 仅公开内容，不可访问任何个人数据 |
| ACT-3 | 现场志愿者 / 辅导员 | 在迎新现场处理系统未解答问题与异常情况 | 管理后台网页 | 未解答问题队列、学生报到状态 |
| ACT-4 | 学校管理员 | 学工、后勤、保卫、学院等多部门分权维护内容 | 管理后台 | 按 RBAC 划分的数据与功能权限 |
| ACT-5 | 系统运维 | 负责部署、配置、监控与故障处理 | 运维后台 / 命令行 | 系统配置、日志、健康状态 |

### 2.3 运行环境

| 类别 | 本地开发环境 | 云端部署环境 |
|---|---|---|
| 服务运行 | 9 个 Spring Boot 服务运行于宿主机 | 9 个服务容器化编排（`docker-compose.prod.yml`） |
| 数据库 | Docker `mysql:8.0.46`，库 `yingxin` | Azure MySQL PaaS（强制 SSL，`MYSQL_SSL_MODE=REQUIRED`） |
| 缓存 | Docker `redis:7.0.15-alpine`，无密码 | 云主机 systemd 部署 Redis 7.0.15（`requirepass`） |
| 运行时 | JDK 17、Node 18+、Maven Wrapper 3.9.12 | 同左，镜像内置 |
| 客户端 | 浏览器（Chrome / Edge） | 浏览器（Chrome / Edge / Safari / 微信内置浏览器），移动端优先适配 |
| 网络 | localhost 直连 | HTTPS + 已备案域名（NFR-4.2） |

> 本地与云端共用同一份 `application.yml`，仅通过环境变量区分，代码零改动。

### 2.4 设计与实现约束

| 编号 | 约束 | 来源 |
|---|---|---|
| C-1 | 后端采用 Maven 多模块微服务，服务前缀 `/api/<服务>/**`，网关转发不裁剪前缀 | AGENTS.md |
| C-2 | 配置一律使用 `${环境变量:本地默认值}` 占位，本地与云端同一份文件 | AGENTS.md |
| C-3 | 前端工程相互独立：`admin-web` 用 Vite 8；`miniprogram`（**已裁剪，见 §8.4.1**）的 Vite 锁死 5.2.8——两者版本本就不同，不得统一升级 | AGENTS.md |
| C-4 | 公共基础设施（统一返回体、全局异常、参数校验、JWT 鉴权）须先定统一方案再逐服务落地，不得各服务自建 | AGENTS.md |
| C-5 | 微信人脸核身等接口需企业主体资质，课程阶段降级为模拟核验 | 技术难点 D5-b |
| C-6 | 学校真实数据（地图、报到流程、身份源）不可获得，全部走可配置的虚构数据 | 技术难点 D4-a / D8 |
| C-7 | 校内服务器与开发机资源有限，9 个服务约需 3.8G 内存，按需启动 | AGENTS.md |
| C-8 | 横向能力必须落到**可运行载体**（`common-core` / `common-web` 两个模块 + 各服务运行基线）；只有文档、没有载体视为未完成 | 本文档 §2.6 |
| C-9 | `common-core` 禁止依赖 servlet / Spring MVC（网关为 WebFlux）；Web 相关能力只能放 `common-web`，且网关不得依赖 `common-web` | 本文档 §2.6.2 |
| C-10 | 服务可运行基线：启动成功 + `/api/<服务>/ping` 返回统一响应体 + Swagger 可访问；未达基线不得进入功能开发 | 本文档 §2.6.1 |
| C-11 | 表结构的新增与变更必须提交迁移脚本；禁止手工改库后不留脚本 | 开发规范 §5.3 |

### 2.6 工程脚手架设计（横向能力的可运行载体）

> 本节解决的问题：横向能力此前**只有文字规范、没有载体**。本节定义"载体长什么样、怎么算跑通"，属于设计基线；
> 具体的类实现留到编码阶段（阶段 S1–S5，见 §2.6.4），**本节不含功能实现**。协议与命名细则见 [开发规范](开发规范.md) 第 1 章。

#### 2.6.1 开箱即用的判定标准

新成员 `git clone` 后，**不写任何业务代码**就应能完成以下 8 项验证（全部通过才算脚手架完备）：

| # | 验证项 | 判定方式 |
|---|---|---|
| 1 | 依赖可下载、**11 个模块**可构建（9 个服务 + `common-core` + `common-web`） | `cd backend && ./mvnw -B clean install -DskipTests` 成功 |
| 2 | 本地基础设施可起 | `docker compose up -d` 后 MySQL / Redis 健康检查通过 |
| 3 | 服务可启动 | 启动任一服务，日志无异常 |
| 4 | 服务自检返回**统一响应体** | `GET http://localhost:8101/api/qa/ping` → `{ "code": 0, "message": "ok", "data": { … } }` |
| 5 | 网关路由可用 | `GET http://localhost:8080/api/qa/ping` 与直连返回一致（前缀不裁剪） |
| 6 | 鉴权边界生效 | 不带令牌访问受保护接口 → HTTP 401 且**响应体结构同上** |
| 7 | 接口文档可打开 | `http://localhost:8101/swagger-ui.html` 可访问且按服务分组 |
| 8 | 测试可执行、CI 全绿 | `./mvnw -pl services/qa-service test` 通过；CI 三个 job 通过 |

#### 2.6.2 模块与依赖（载体的结构）

| 模块 | 定位 | 内容（包 / 类清单） | 允许依赖 |
|---|---|---|---|
| `backend/common-core` | 无 Web 依赖的公共内核 | `common.core.result`：`Result`、`PageResult`；`common.core.error`：`ErrorCode`、`BizException`；`common.core.constant`：`HeaderNames`（`X-User-Id` / `X-User-Role` / `X-Trace-Id`）、`CacheKeys`；`common.core.context`：`UserContext`（纯 POJO）；`common.core.util`：`IdUtil`、`JsonUtil` | JDK、Jackson、Lombok。**禁止** spring-web / spring-webmvc / servlet-api |
| `backend/common-web` | MVC 服务专用能力 | `common.web.advice`：`GlobalExceptionHandler`；`common.web.filter`：`TraceIdFilter`、`UserContextFilter`；`common.web.config`：`MybatisPlusConfig`（分页、审计字段填充）、`JacksonConfig`、`RedisConfig`、`ValidatorConfig`；`common.web.support`：`CurrentUserArgumentResolver` | `common-core` + `spring-boot-starter-web` + MyBatis-Plus + validation + Redis |
| `backend/services/gateway` | 入口与鉴权 | 路由配置、CORS、`AuthGlobalFilter`（令牌校验 + 白名单 + 用户上下文注入） | **仅** `common-core`（用于 401 的统一响应体） |
| `backend/services/*`（8 个） | 业务服务 | 运行基线 + 业务代码（业务代码按 §4 功能需求实现） | `common-web` |

依赖方向（单向）：

```
gateway ──► common-core
services/* ──► common-web ──► common-core
```

#### 2.6.3 服务运行基线（每个服务的固定形态）

| 项 | 约定 |
|---|---|
| 目录 | `services/<name>/src/main/java/com/sicnu/yingxin/<sn>/`，`resources/` 下 `application.yml` 与 `mapper/.gitkeep` |
| 必备类 | `<Name>Application`（启动类）、`controller/PingController`（自检，返回统一响应体）；**gateway 除外**——仅有启动类与路由配置，不提供自检接口 |
| 端口 | gateway 8080、auth 8100、qa 8101、checkin 8102、navigation 8103、aid 8104、life 8105、content 8106、admin 8107（不得擅自变更） |
| 配置 | 一律 `${环境变量:本地默认值}`；本地与云端同一份文件（C-2） |
| 容器化 | 每个服务一个多阶段 `Dockerfile`（构建上下文为 `backend/`） |
| 自检 | `/api/<服务>/ping` 返回 `code=0`；`/actuator/health` 为 `UP` |
| 日志 | 输出到 stdout，格式含 `traceId`（可被容器采集） |

#### 2.6.4 落地顺序（基建先行，与业务功能分开排期）

| 步骤 | 内容 | 完成判定 |
|---|---|---|
| S1 | 建 `common-core`（响应体、错误码、业务异常、常量、工具） | 单元测试可断言 `Result` 序列化结果与错误码取值 |
| S2 | 建 `common-web`（全局异常、traceId、用户上下文、MyBatis-Plus 与 Redis 配置） | 任一服务引入后：ping 返回统一体、抛业务异常得到对应错误码、日志带 traceId |
| S3 | 网关统一鉴权过滤器 + 白名单 | 不带令牌 401（统一体）；`/api/*/ping`、`/api/auth/login/**` 放行 |
| S4 | 集中式迁移脚本目录 + 首批表（按 §7.1 裁剪后的实体） | 脚本可从空库执行到完整表结构 |
| S5 | 单服务纵向打样（建议 qa-service） | Controller → Service → Mapper → Redis 全链路跑通且带单元测试，作为其余服务的模板 |

> 顺序理由：S1–S2 是所有服务的公共前置（C-4）；S3 打通前端已在使用的 `Bearer` 链路（F11.6）；
> S4 是功能开发的数据前提；S5 产出可复制的样板，避免 9 个服务各写一套。

#### 2.6.5 明确不引入（防脚手架膨胀）

| 不引入 | 理由 | 何时重新评估 |
|---|---|---|
| 服务注册与配置中心（Nacos） | 服务地址由环境变量固定即可（Q-8） | 服务实例超过 1 台/服务时 |
| 消息队列（MQ） | 本期无异步刚需，统计允许最终一致（DI-21） | 出现跨服务异步或削峰需求时 |
| 分布式事务 / 分布式锁 | 同库分表 + 唯一索引 + 乐观锁已足够（DI-3、DI-8） | 出现跨库写时 |
| 代码生成器、多环境 profile 矩阵、K8s | 课程项目规模不需要 | 不评估 |

### 3.3 业务流程分析

**报到主流程（目标态）**：

```text
身份核验登录
  → 解析身份（本科/研究生、学院专业、宿舍楼栋、报到批次）
  → 生成个性化欢迎语与专属报到清单
  → 线上预报到（信息填报）
  → 缴费（或绿色通道 / 缓交申请）
  → 到校领物资
  → 宿舍入住
  → 人脸采集
  → 校园卡激活
  → 报到完成（可查凭证二维码）
```

**异常分支**：

| 异常场景 | 处理路径 |
|---|---|
| 未缴费 | 引导至缴费入口，或跳转绿色通道 / 缓交申请 |
| 材料缺失 | 展示材料清单与补交办理地点、联系人电话 |
| 暂缓报到 / 改期 | 展示申请流程与审批人联系方式 |
| 问答未命中 | 落库未解答记录，转人工（志愿者 / 辅导员） |
| 身份信息缺失字段 | 隐藏对应模块并提示到现场核实 |

![时序图-微信登录与网关鉴权](架构图/04-时序图-微信登录与网关鉴权.svg)

*图 6-1 时序图 · 微信一键登录与网关统一鉴权（对应附录 A FIG-04）*

时序覆盖三段：**首次登录**（`wx.login` 取临时 code → 经网关按路径转发至 auth-service → `code2session` 换 openid → 按 openid 查绑定关系，未绑定则新建用户并绑定、解析身份 → 写入 Redis 会话并设置 TTL → 返回 `{ code, message, data }` 与 token，前端同时存 Pinia 与 localStorage 的 `yingxin_token`）；**携带令牌访问**（`Authorization: Bearer <jwt>`，网关校验存在性、有效期与续期策略，有效则注入用户上下文后转发，缺失或失效返回 401，前端清除本地 token 并跳转登录）；**登出**（删除会话，令牌立即失效）。

图中同时标注了 F11.6 统一鉴权的目标态与现状：目标为网关 Filter 统一校验、白名单放行 `ping` / `login`；现状为尚无拦截器或 Filter，前端下发的 Bearer 令牌无人校验，属需优先补齐的基础设施（对应约束 C-4、NFR-4.1）。FR-1.8 的令牌续期策略与 §5.4 的传输安全要求在此链路上一并落地。

#### 7.1.3 全局口径（所有表适用）

| 项 | 要求 |
|---|---|
| 通用字段 | 每张表必须包含 `id`、`create_time`、`update_time`、`create_by`、`update_by`、`deleted`，由持久层自动填充，业务代码不得手写 |

### 7.2 数据完整性要求

> 本节为**可判定的完整性规则**：每条有编号、校验时机与违反时的行为，可直接转成测试用例。
> 本项目**不使用物理外键**，建模工具画出的关系线只是逻辑关系，数据库不会替我们校验——因此规则必须逐条落到代码。

| 编号 | 完整性规则（可判定） | 校验时机 | 违反时的行为 |
|---|---|---|---|
| DI-1 | 每张表必须有主键，主键非空且唯一 | 建表 + 每次写入 | 建表即约束；写入失败按系统错误返回 `code 9002` |
| DI-2 | 业务唯一键不得重复：学号、openid、unionid、管理员用户名、角色编码、报修单号、凭证号、配置键 | 写入 / 更新 | 唯一索引拦截，返回 `code 2004`，提示"记录已存在" |
| DI-3 | 报到打卡幂等：同一 (user_id, 步骤编码) 只能有一条未删除记录 | 打卡请求 | 返回首次打卡结果（`code 0`），**不新增记录** |
| DI-4 | 打卡时间必须落在该批次的报到时间窗口内 | 打卡请求 | 拒绝，返回 `code 2301` 并提示窗口起止时间 |
| DI-5 | 同一用户同一批次最多一张有效报到凭证 | 签发凭证 | 不重复签发，返回既有凭证（`code 0` + 现有凭证信息） |
| DI-6 | 同一 (user_id, 政策, 批次) 只允许一份非终态资助申请 | 提交申请 | 不新建，返回既有申请单号（`code 0` + 单号） |
| DI-7 | 资助申请置为"已驳回"时，驳回理由必须非空且长度 2–255 | 审核提交 | 拒绝更新，返回 `code 2502` |
| DI-8 | 审核类更新必须携带乐观锁版本号，版本不匹配即视为并发冲突 | 审核更新 | 拒绝更新，返回 `code 2003`，提示刷新后重试 |
| DI-9 | 状态只能沿状态机允许的转移变化，不得跳变 | 每次状态更新 | 拒绝更新，返回 `code 2002`（当前状态不允许该操作） |
| DI-10 | 路网数据自洽：边的两端必须存在于节点集合、`(起点, 终点)` 唯一、禁止自环（地图数据**不入库**，因此在**文件加载时**校验） | 服务启动加载 `road-network.json` 时 | 启动失败并打印违规条目（不产生运行时错误码） |
| DI-11 | 所有引用字段（各类 id、步骤编码、政策 id、**点位编码**等）写入前必须指向存在且未删除的记录；引用静态资源（`poi_code`）时须存在于已加载的 POI 集合 | 写入 / 更新 | 拒绝写入，返回 `code 2001`（引用的资源不存在） |
| DI-12 | 停用或下线的模板与内容不得影响历史数据：历史进度、申请、凭证、学习记录仍可查询 | 停用 / 下线 | 不阻断该操作；历史记录保持可读，不做级联停用 |
| DI-13 | 逻辑删除语义固定：`deleted = 0` 为未删除，删除时写入该行主键值；唯一索引末位必须包含 `deleted` | 每次删除 / 写入 | 违反唯一索引时同 DI-2；查询条件漏带 `deleted = 0` 视为缺陷（评审必查，多表关联时尤其注意） |
| DI-14 | 时间顺序：创建时间 ≤ 更新时间；提交时间 ≤ 审核时间；签发时间 < 过期时间；撤回时间 > 发布时间 | 写入 / 更新 | 拒绝写入，返回 `code 3003`（取值越界） |
| DI-15 | 业务时间一律以服务端时间为准，前端传入的时间字段一律忽略 | 接口入参处理 | 忽略前端值且不报错，按服务端时间落库 |
| DI-16 | 枚举与取值域：状态与类别只能取登记集合；经纬度在合法范围；金额非负且保留 2 位小数 | 写入 / 更新 | 拒绝写入，返回 `code 3003` |
| DI-17 | 格式约束：学号 4–32 位数字或字母、手机号 `^1[3-9]\d{9}$`、身份证 18 位含校验位、富文本过滤脚本标签 | 写入 / 更新 | 拒绝写入，返回 `code 3002`（格式非法） |
| DI-18 | 空值语义固定：未填写一律为 `NULL`，不得用空字符串或 0 代替；"未知"与"不适用"须在字段说明中区分 | 建模与评审 | 字段定义不符合即视为缺陷，须在实现前修正 |
| DI-19 | 审计类表（操作日志、登录日志、埋点、提问日志、报修流转）只允许新增，业务代码不得出现 UPDATE / DELETE | 代码评审 + 数据库账号权限 | 评审拦截；建议数据库账号不授予这些表的 UPDATE / DELETE 权限 |
| DI-20 | 关键变更（审核、发布、配置修改、权限调整）必须留痕：**同一服务内**与操作日志同一事务成对写入；**跨服务**时由发起方在业务成功后追加日志，业务失败则不记日志（允许秒级延迟） | 变更操作 | 同服务内任一步失败则整体回滚，返回 `code 9002`；跨服务以业务写入结果为准 |
| DI-21 | 看板数据来自埋点表聚合，允许最终一致（延迟不超过 5 分钟） | 看板查询 | 允许展示延迟数据；业务判定（如是否已报到）必须查业务表，不得读看板 |
| DI-22 | 跨服务写操作必须带幂等键：调用方先落本地事务再调用下游，下游失败时登记待重试状态 | 跨服务调用 | 不回滚本地已提交数据，改为登记重试并按幂等键去重 |

| DR-Q3 | 报到进度记录 | 约 45,000 条/批（每生 7–10 条） | 长期保留 |
| DR-Q4 | 报到凭证 | 5,000 条/批 | 长期保留（含核销记录） |

| DR-Q7 | POI / 路网（**静态文件，不入库**） | POI 20–30、节点 50–100、边 100–200 | 随代码版本管理，直接替换文件（C-6） |
| DR-Q8 | 资助申请与材料 | 数百条/批 | 长期保留（材料文件外置存储） |
| DR-Q9 | 报修单 | 数百条/批 | 长期保留 |

> 归档与冷热分离的**实现**建议本期不做（理由见 §8.4）。

### 7.4 数据安全与权限要求

| 级别 | 数据 | 要求 |
|---|---|---|
| L1 公开 | 政策、问答、内容、社团、公告、POI、生活服务信息 | 可对家长 / 访客开放（ACT-2） |
| L2 内部 | 报到进度、报修单、看板汇总 | 登录后按本人或角色可见 |
| L3 个人敏感 | 姓名、手机号、学号、宿舍、资助申请理由、报修照片 | 加密存储 + 展示脱敏 + 按权限访问 |
| L4 高敏 | 身份证号、人脸核验结果、完整对话记录 | 加密存储、最小化采集、禁止明文出接口与进日志 |

关键要求（对应第 5 章安全需求）：

- 存储加密：L3 / L4 字段必须密文落库；密钥走环境变量，禁止入库入仓（算法与托管方式见 [数据建模](数据建模.md) 附录 A）；
- 传输加密：全链路 HTTPS（NFR-4.2）；
- 脱敏：手机号 `138****5678`、身份证 `3301**********1234`、姓名 `张*`；日志禁止打印令牌、密码、完整身份证与手机号；
- 令牌：JWT 只放 `userId` / `role` / `exp`，不含任何隐私字段；
- 权限：后台按角色（学工 / 后勤 / 保卫 / 学院 / 资助审核 / 运维）划分功能权限与数据范围；学生接口一律按"本人"过滤，`userId` 取自网关注入的请求头，**不接受前端传参**；
- 隐私边界：家长 / 访客不得通过任何接口获取个人数据，包括"某学生是否已报到"这类间接信息（NFR-4.7）；
- 看板只出聚合值，小样本（少于 5 人）不单独展示，避免反推个人；
- 课程演示使用虚构数据，**严禁把真实学生数据导入开发库**（C-6）。

#### 8.4.3 明确不建议回退的（虽显"重"）

| 项 | 原因 |
|---|---|

| 逻辑删除字段改用 `BIGINT` | 解决"逻辑删除 + 唯一索引"冲突，改动成本约等于 0（待 §8.4 决策项确认） |
