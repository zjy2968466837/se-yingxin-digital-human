# 数据表存储结构规划

> **文档定位**：回答"24 张表在磁盘上长什么样"——引擎、字符集、行格式、主键与索引、页数与容量、增长与归档。字段级定义见 [数据建模](数据建模.md) §3，建表语句见 [`backend/db/migration/`](../backend/db/migration/)，表关系见 [数据建模](数据建模.md) §4。
> **实测口径**：2026-10-27，`mysql:8.0.46` 容器，按版本号顺序执行 9 个迁移脚本；容量数字为"合成数据实测 + 一期 5,000 新生量级推算"，方法见 §3.1。
> **配套**：[MySQL 存储引擎与执行计划](MySQL存储引擎与执行计划.md)（页/索引/执行计划的原理与参数）。

## 1 全库统一存储基线

| 项 | 取值 | 依据/实测 |
|---|---|---|
| 实例 / 库 | 单实例，单库 `yingxin` | [开发规范](开发规范.md) §5；9 服务同库避免分布式事务 |
| 存储引擎 | `InnoDB` | 24/24 表实测；需要事务、行锁、崩溃恢复 |
| 字符集 | `utf8mb4` | 中文、emoji 均可存 |
| 排序规则 | `utf8mb4_unicode_ci` | 24/24 表实测；与云端一致 |
| 行格式 | `DYNAMIC` | 24/24 表实测；大字段溢出到独立页 |
| 页大小 | 16 KB | `innodb_page_size`，建实例后不可改 |
| 表空间 | 独立表空间（`innodb_file_per_table=1`） | 每表一个 `.ibd`，删表可还盘 |
| 主键 | `BIGINT` 雪花 ID，聚簇索引 | 趋势递增，插入落在 B+ 树右端，页分裂少 |
| 物理外键 | 无 | 实测 0 个；引用完整性由应用层保证（[数据建模](数据建模.md) §6） |
| 分区 | 不分区 | 一期单表最大约 10 万行，见 §6 |
| 时间类型 | `DATETIME(3)`（7 字节） | 毫秒精度，应用层填充，不写 `DEFAULT CURRENT_TIMESTAMP` |
| 逻辑删除 | `deleted BIGINT`，0=未删 | 唯一索引末位带 `deleted`，支持删除后重建同业务键记录 |

排序规则的一个副作用需要知道：`utf8mb4_unicode_ci` 大小写不敏感，`admin_user.username` 上建唯一索引后，`Admin` 与 `admin` 视为同一用户。这是可接受的行为（登录名不区分大小写），但**不能**用它存大小写敏感的令牌/编码；这类值应改用 `_bin` 排序规则或 `VARBINARY`。当前 24 张表没有这种列。

三个需要注意的物理细节：

1. `qa_question` 的全文索引不是普通 B+ 树：InnoDB 会建 6 张 `fts_*_index_1..6` 辅助表，并给主表加隐藏列 `FTS_DOC_ID`（连同 `FTS_DOC_ID_INDEX`）。它的空间不计入 `information_schema.tables.index_length`，容量评估要单独看（§3.4）。
2. `uk_*` 索引末位带 `deleted`（如 `uk_user_step`、`uk_guide_type`、`uk_user_policy_batch`）：删除时写入本行 `id` 而不是 1，保证"删掉后还能重建同业务键记录"。代价是**历史删除行仍占索引空间**，需要定期清理（§6）。
3. `admin_user_role.idx_role` 与 `content_article.uk_guide_type` 由增量脚本补建（`V20261025134001`、`V20261025134002`），不在 init 脚本里，重建库时必须按版本号顺序执行全部 9 个脚本。

## 3 容量估算

### 3.1 方法

```
行宽 ≈ 定长列字节 + 变长列业务平均长度 + 27 B 行开销
        （5 B 行头 + 6 B trx_id + 7 B roll_ptr + 空值位图/对齐）
数据页 ≈ 行数 × 行宽 ÷ (16 KB × 0.75)      -- 0.75 为 B+ 树平均填充率
索引   ≈ 数据 × 索引系数                   -- 实测大表 0.16–1.0，见 §3.4
```

变长列按**业务平均长度**算，不按 `VARCHAR(n)` 上限——按上限估会把容量放大 3–10 倍。

### 3.3 多批次增长

固定表（模板、角色、配置、政策、服务信息、问答库、内容、公告）不随批次增长；其余按批次线性叠加：

| 口径 | 估算 | 说明 |
|---|---:|---|
| 单批（第 1 年） | ≈ 126 MB | §3.2 |
| 三批（第 3 年） | **≈ 380 MB** | 固定表 2 MB + 变动表 126 MB × 3 |
| 归档后稳态 | ≈ 150 MB | `qa_ask_log`/`admin_behavior_event`/`admin_operation_log` 按月归档，明细不累积 |

预算：在线库 **< 5 GB**、单表 **< 1,000 万行**。超过这个量级再评估分区或分库；按当前增长，课程周期内不需要。

## 4 大字段与溢出页

| 表.列 | 类型 | 处理建议 |
|---|---|---|
| `qa_message.content` | TEXT | 单条对话可能较长；列表查询只取 `id/role/create_time`，正文按需单查 |
| `qa_question.answer` | MEDIUMTEXT | 富文本答案；列表页只查 `question/category/status` |
| `content_article.content` | MEDIUMTEXT | 正文可达数百 KB，`DYNAMIC` 下走溢出页；接口分"列表摘要"与"详情正文"两个查询 |
| `admin_operation_log.detail` / `before_value` / `after_value` | TEXT/JSON | 审计用，只在详情页读；归档时整行导出 |
| `qa_question.media` / `life_repair_order.images` / `aid_policy.match_rule` | JSON | 弱结构化；可检索字段必须单独成列（[数据建模](数据建模.md) §1.2） |

硬规则：**禁止 `SELECT *`**。`DYNAMIC` 行格式下大字段溢出到独立页，`SELECT *` 会把溢出页一起读进来，一条列表查询可能放大 10 倍 I/O。

## 5 索引的物理代价

- 二级索引叶子存"索引列 + 主键"，因此 `BIGINT` 主键（8 B）会出现在每个二级索引里；主键越宽，所有二级索引越大。
- `checkin_progress` 的索引体积与数据体积接近 1:1：3 个二级索引，其中 `uk_user_step` 是 3 列索引。这是"报到进度按用户/步骤/状态都能查"的代价，属于有意设计。
- 组合索引列序按"等值列在前、范围列在后"排（`idx_status_time(status, create_time)`）；把 `create_time` 放前面会让状态过滤失效（见 [MySQL 存储引擎与执行计划](MySQL存储引擎与执行计划.md) §5.5 Q9 的反例）。
- 低基数列不建单列索引（`status`、`category`、`event_type` 基数 ≤ 6），统一并入组合索引；行数 < 100 的小表不建二级索引（[数据建模](数据建模.md) §1.4）。
- 日志表的索引只保留时间/主体维度，写入密集时索引越多，redo 与刷脏压力越大。

## 6 分区与归档

**一期不分区**，理由：

1. 最大表约 10 万行、30 MB，分区带来的扫描裁剪收益可以忽略；
2. MySQL 分区要求分区键出现在**每个唯一索引**里；本项目主键是雪花 `id`，按时间分区就必须把时间列塞进主键，破坏"单列雪花主键"的统一口径；
3. 分区表的 `ALTER`、统计信息与备份都更复杂，课程环境维护成本高于收益。

**归档**（依据 [数据建模](数据建模.md) §7.3）：

| 表 | 策略 | 存储影响 |
|---|---|---|
| `qa_ask_log` | 按月导出汇总后删明细，保留 6 个月 | 稳定在约 6 个月量级 |
| `admin_behavior_event` | 按月导出日粒度汇总后删明细 | 同上，是最大的表 |
| `admin_operation_log` | 归档不删（审计要求） | 线性增长，属预期 |
| `qa_message` / `qa_session` | 学期结束归档（导出冷存储后清理） | 对话含 L4 数据，最小化保留 |
| 逻辑删除行 | 定期物理清理超期 `deleted<>0` 的行 | 唯一索引末位带 `deleted`，不清会持续膨胀 |

注意：`DELETE` 只释放页内空间，`.ibd` 不会变小。归档后要看 `information_schema.tables.data_free`，需要还盘时执行 `OPTIMIZE TABLE`（在线重建，期间占用额外空间，安排在低峰）。

核对 SQL：

```sql
-- 表数量与外键
SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='yingxin';
SELECT COUNT(*) FROM information_schema.referential_constraints WHERE constraint_schema='yingxin';

-- 引擎/行格式/排序规则是否统一
```

## 8 运维检查

```sql
-- 1) 表大小与碎片（归档后重点看 free_mb）
SELECT table_name,
       table_rows,
       ROUND(data_length/1024/1024, 2) AS data_mb,
       ROUND(index_length/1024/1024, 2) AS index_mb,
       ROUND(data_free/1024/1024, 2)    AS free_mb
FROM information_schema.tables
WHERE table_schema='yingxin' ORDER BY (data_length+index_length) DESC;

-- 2) 索引页数（判断索引是否异常膨胀）
SELECT table_name, index_name,
       MAX(CASE WHEN stat_name='size' THEN stat_value END)          AS pages,
       MAX(CASE WHEN stat_name='n_leaf_pages' THEN stat_value END)  AS leaf_pages
FROM mysql.innodb_index_stats
WHERE database_name='yingxin' GROUP BY table_name, index_name
ORDER BY pages DESC;

-- 3) 候选清理：逻辑删除行占比（deleted 写入的是行 id，不是 1）
SELECT 'checkin_progress' AS t, COUNT(*) AS total,
       SUM(deleted <> 0) AS deleted_rows FROM checkin_progress
UNION ALL
SELECT 'qa_question', COUNT(*), SUM(deleted <> 0) FROM qa_question;
```

阈值建议：单表 `free_mb > 数据量 30%` 时安排 `OPTIMIZE TABLE`；`qa_ask_log`/`admin_behavior_event` 明细行数超过 6 个月量级时检查归档任务；索引页数连续两月增长而数据量不变，排查是否有重复索引或长事务未提交。
